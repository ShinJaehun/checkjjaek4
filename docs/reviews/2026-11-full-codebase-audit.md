# 책짹 전체 코드베이스 감사 — 부분 감사 결과

## 1. 감사 개요 및 검토 범위

2026-11-28 기준, `audit/full-codebase-review` 브랜치의 `b7d3f6c`를 검토했다. 기준은 저장소의 `AGENTS.md`, 활성 기능 명세, 권한·가시성 아키텍처, 실제 Rails 요청 경로와 기존 테스트다. 파일 위치는 이 커밋의 줄 번호다.

라우트와 DB 스키마에서 주요 도메인을 식별하고, 아래에 명시한 경로를 선별해 controller → policy/scope → model/service → 응답 또는 뷰 순으로 추적했다. **확인**은 코드로 결과가 결정된다는 뜻이다. **조건부 위험**은 필요한 조건과 보호 누락을 코드에서 식별했지만 동시 실행이나 운영 환경에서 결과를 관찰하지 않았다는 뜻이다. 명세 사이의 충돌은 별도로 표시했다. RSpec·브라우저·운영 환경 검증은 수행하지 않았다.

## 2. 종합 평가

**우선 조치 대상은 P1 두 건이다.** 원문의 공개 범위를 좁히면 기존 다시짹에 대한 정당한 운영 조치가 실패하는 경로를 확인했다. 동아리 재운영은 사용자와 동아리를 잠그지만, 잠금 획득 시점에 이미 탈퇴한 요청자인지를 검사하지 않는다. 두 건 모두 개별 기능의 정상 경로가 아니라 서로 다른 기능이 같은 데이터의 상태를 바꿀 때 발생한다.

검토한 경로에서 P0에 해당하는 권한 우회나 치명적 데이터 손실을 확정하지 않았다. 전체 코드베이스에 P0가 없다는 판정은 할 수 없다. 아래 P2·P3 항목에는 사용자에게 실제로 나타나는 불일치, 확인된 반복 비용, 정책 결정이 필요한 사례를 구분했다.

## 4. 논리적 오류 및 보안·데이터 무결성

### 4.1 P1 · 확인 — 원문 공개 범위를 좁히면 기존 다시짹 숨김·복구가 실패한다

- **경로와 결과.** 운영자 권한 판정은 `app/policies/jjaek_policy.rb:186`에서 시작한다. `app/services/jjaeks/hide.rb:24`와 `restore.rb:27`은 대상의 `hidden_at`만 바꾸지만 `update!`는 모델 전체를 검증한다. `app/models/jjaek.rb:43`에 등록된 검증은 이미 존재하는 인용에도 적용된다. 공개 원문에 달린 다시짹을 유지한 채 원문을 비공개로 바꾸면 `:294`에서 거부된다. 원문을 책친구 공개로 좁히고 다시짹이 전체 공개이면 `:315`에서도 거부된다. 관리자 controller는 이를 422로 처리한다. 숨김·복구와 대응 감사 행 모두 저장되지 않는다.
- **정책과 테스트.** 살아 있는 원문의 권한 변경은 인용 연결을 보존하고 현재 독자의 접근만 다시 판단하도록 정한다. 운영자의 숨김·복구 자격에는 별도 조건이 있다. 기존 `spec/services/jjaeks/hide_spec.rb:19`의 문맥별 숨김은 인용 생성 **이후** 원문의 공개 범위가 축소된 경우와 다르다. [가시성 기준](../architecture/jjaek_visibility.md) · [운영 조치 명세](../specs/moderation_mvp.md)
- **최소 수정과 영향.** moderation 상태만 변경할 때 기존 인용의 생성 조건을 재적용하지 않도록 검증 시점을 좁힌다. 신규 인용·목적지·공개 범위 변경 검증과 조치·감사 행의 원자성은 보존해야 한다. 공개 범위 축소 후 숨김 한 사례와, 숨김 뒤 원문을 비공개로 바꾼 후 복구 한 사례에서 감사 행과 일반 독자의 접근 결과를 함께 확인한다.

### 4.2 P1 · 조건부 위험 — 계정 탈퇴 뒤 이미 시작된 재운영 신청이 대기 상태를 다시 만들 수 있다

- **확인한 경계.** `app/services/users/withdraw_account.rb:25`는 사용자를 잠그고 관리 동아리를 검사한다. 이미 재운영 대기 중이면 신청을 취소하고(`:57`), 회원 관계도 정리한다(`:95`). 종료된 동아리의 `group_admin_id`는 역사적 관리자로 보존한다. 반대 경로인 `app/controllers/groups/reactivation_requests_controller.rb:8`도 사용자 → 동아리 순서로 잠그고 재인가한다. 그러나 `app/policies/group_policy.rb:117`은 비활성 동아리, 운영 상태, 관리자 ID를 검사할 뿐 요청자의 탈퇴·계정 정지 상태를 검사하지 않는다. `app/models/group.rb:116`의 관리자 판정은 ID 비교다.
- **순서에 따른 차이.** 재운영이 먼저 커밋되면 탈퇴가 신청을 취소한다. 재운영 요청의 최초 인증·페이지 인가 후 탈퇴가 먼저 커밋되면, 잠금 안에서 읽은 사용자도 같은 관리자 ID를 가지므로 이미 진행 중이던 요청이 `pending_approval!`까지 도달할 수 있다. 이후 승인 경로(`app/controllers/admin/group_approvals_controller.rb:11`)에도 탈퇴한 관리자의 활성 회원 관계를 복구하는 처리는 없다. 실제 경합이나 운영 데이터 발생 여부는 확인하지 않았다. [탈퇴와 재운영 정책](../specs/account_group_lifecycle.md)
- **최소 수정과 영향.** 재운영 신청의 사용자 잠금 안에서 기존 `with_active_user_lock`과 동일한 계정 조건을 검사한다. 동아리의 과거 관리자 참조는 보존한다. 기존 `spec/requests/personal_reading_concurrency_spec.rb:25`의 독립 요청 패턴으로 탈퇴가 먼저 끝난 순서에서 동아리 상태, 재운영 사건 수, 알림 수를 확인한다. 변경 영향은 정상 관리자의 재운영과 계정 종료 사이의 경계다.

### 4.3 P2 · 확인 — 댓글은 저장됐지만 알림 저장 오류가 작성 실패로 전달된다

`app/controllers/comments_controller.rb`의 `create`는 `with_reaction_lock`에서 댓글을 저장한 뒤 별도로 `Notification.notify_comment_created`를 호출한다. `app/models/notification.rb:99`에서 수신자를 정하고 `:132`의 `find_or_create_by!`에서 발생한 저장 예외는 성공 응답까지 전파된다. 사용자가 다시 제출하면 이미 저장된 댓글과 같은 댓글을 한 번 더 남길 수 있다. 배지 broadcast의 예외 처리(`:57`)는 Notification 행 자체의 저장 실패를 처리하지 않는다. 동아리 사건 알림에는 이미 커밋 후 수신자별 실패 처리 관례가 있다. [오류 피드백 기준](../specs/error_feedback.md) · [알림 명세](../specs/notifications_mvp.md)

최소 수정은 댓글 저장 실패와 파생 알림 실패의 응답을 구분하는 것이다. 알림 저장 오류만 발생시킨 request spec에서 댓글 한 건과 성공 응답을 확인한다. 알림 전달 보장이나 자동 재시도는 별도 결정이 필요하다.

## 5. 기능·정책·UI 일관성

- **P2 · 확인 — 초대 메일 실패 시 복구 경로가 관리자에게 전달되지 않는다.** `app/controllers/admin/registration_invitations_controller.rb:14`에서 초대를 저장한 뒤 동기 발송하고, 재발송도 `:28`에서 토큰 교체를 커밋한 뒤 발송한다. SMTP 실패 시 초대 행은 남고 재발송 전 토큰은 이미 무효다. 같은 이메일로 신규 생성하면 중복으로 거부된다. `spec/requests/registration_invitations_spec.rb:100`은 성공 안내를 막지만 예외 전파 자체를 기대한다. 전송 오류를 구분해 기존 초대에서 재발송할 수 있도록 안내하고, 테스트는 성공 안내 부재와 기존 행 재사용을 확인하는 것이 적절하다. 토큰 원문을 보관하거나 실패 후 과거 토큰을 되살릴 필요는 없다. [초대 정책](../specs/registration_invitations_c08.md)
- **P2 · 확인 — 권한 변경이 과거 동아리 운영 이력의 역할 표기를 바꾼다.** `app/views/groups/_platform_operation_history_entry.html.erb:14`와 `_operation_history.html.erb:34`가 `app/helpers/application_helper.rb:88`을 호출한다. 이 helper는 사건의 종류와 무관하게 *현재* `actor.global_admin?`로 역할을 고른다. 플랫폼 운영 정지를 수행한 사람이 나중에 강등되면 같은 이력에 플랫폼 조치 배지와 ‘동아리 관리자’가 함께 표시될 수 있다. 감사 행이나 현재 권한이 바뀌는 문제는 아니다. 플랫폼 전용 사건은 사건 종류에서 역할을 구하고, 과거 역할을 확정할 수 없는 사건에는 처리자 이름만 표시하는 방법이 있다. 역할 변경 전후 동일 이력 표시 한 사례면 된다. [운영 이력 기준](../specs/account_group_lifecycle.md)
- **P2 · 정책 확인 필요 — 탈퇴 익명화와 개인 다시짹의 과거 이름 스냅샷.** `app/models/jjaek.rb`의 `mark_requotes_as_deleted_source`는 개인 다시짹에 원문 작성자의 당시 이름을 복사하고 원문 ID를 해제한다. `app/views/jjaeks/_deleted_quoted_source.html.erb:3`은 그 문자열을 그대로 표시한다. 원문 삭제 후 작성자가 탈퇴하면 익명화된 User 이름과 과거 스냅샷이 달라진다. 해당 개인 다시짹은 작성자 전용이고, 동아리 다시짹은 이름을 저장하지 않는다. 개인 삭제 안내의 스냅샷 보존과 탈퇴자 익명 표시 중 어느 규칙이 이 경우에 우선하는지 명시할 필요가 있다. 동명이인이 있으므로 기존 행을 이름으로 일괄 치환하는 방식은 위험하다. ## 6. 중복 구현 및 불필요한 구조

- **P2 · 확인 — 책 상세 댓글 변경이 존재하지 않는 두 번째 목록까지 렌더링한다.** 현재 책친구 활동 카드는 `app/views/books/_friend_activity.html.erb:7`에서 독서 활동 문장을 그린다. 댓글 패널은 책짹 목록에 있다. 그런데 `app/views/comments/create.turbo_stream.erb:4`, `update.turbo_stream.erb:4`, `destroy.turbo_stream.erb:3`는 개인 책 문맥에서 `_sync_book_comments_list.turbo_stream.erb:6`을 통해 다른 문맥용 댓글 목록 전체도 렌더링한다. 브라우저가 없는 대상을 무시해도 서버 렌더 비용과 응답 바이트는 발생한다. 일반 책 상세 응답에서 실제 목록 하나만 갱신하는 것이 가장 작은 변경이다. `spec/requests/comments_spec.rb:217`에서 직접 요청하는 기존 `book_friend` 문맥의 호환성은 별도로 판단해야 한다. [책 상세 활동 기준](../specs/book_activity_mvp.md)
- **P3 · 확인 — 세 알림 서비스에 동일한 전달 절차가 있다.** `app/services/notifications/group_membership_notifier.rb`, `group_lifecycle_notifier.rb`, `moderation_notifier.rb`의 `schedule`과 `deliver_to`가 커밋 후 수신자 순회, 본인 제외, 수신자별 실패 로깅, 고유 충돌 확인을 각각 구현한다. 수신자 결정·사건 매핑은 실제로 다르다. 전달 실패 처리에 다음 변경이 생길 때 공통 절차만 추출할 만하다. 영향 범위는 세 사건군의 알림 시점과 중복 억제이므로 기존 rollback·중복·개별 실패 테스트를 유지한다.
- **파셜 통합 판단.** 일반 책 검색 카드와 첨부용 검색 카드는 이미 `book_searches/_result_card_layout.html.erb`를 공유하며, 첨부 선택과 책장 등록은 별개 작업이다. 동아리 관리자용 `groups/contents/_timeline_row.html.erb`도 플랫폼 관리 목록과 본문·검색·조치 노출 기준이 다르다. 두 쌍 모두 추가 통합을 권할 근거가 없다. 댓글의 중복 응답을 먼저 줄이는 편이 실제 호출 경로를 단순하게 만든다.

## 8. 우선순위별 개선 권고

1. **P1** — 다시짹 숨김·복구의 순차 사례 두 개를 먼저 고정한다. 같은 우선순위로 탈퇴가 먼저 끝나는 재운영 사례를 PostgreSQL 독립 연결로 검증한다. 전자는 코드로 확인된 운영 기능 오류이고 후자는 실제 발생 빈도를 모르는 상태 전이 위험이다.
2. **P2** — 이미 커밋된 댓글과 초대가 실패 화면으로 끝나는 경로, 이력의 역할 표시를 우선 다룬다. 개인 스냅샷은 제품의 보존 결정을 먼저 받는다. 중복 댓글 렌더·알림함 비용·운영 이력 조회는 각각 독립적으로 개선할 수 있다.
3. **P2·P3** — 기존 JS 테스트를 CI에 연결한다. 알림 서비스 통합은 전달 동작을 수정할 때 함께 검토한다.

## 9. 미검토 영역 및 추가 확인 순서

| 순서 | 남은 검토 | 필요한 근거 |
