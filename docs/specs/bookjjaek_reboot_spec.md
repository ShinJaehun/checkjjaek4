# Bookjjaek Reboot Spec

## 목적

이 문서는 checkjjaek4를 기존의 post 중심 SNS 구조에서
**Jjaek 흐름을 중심으로 하고 책과 서재를 중요한 문맥으로 다루는 독서 커뮤니티 서비스**로
재정의하기 위한 기준 문서다.

이 문서는 아래를 고정한다.

- 제품의 핵심 방향
- 핵심 용어
- 핵심 도메인 모델
- 관계 모델
- 공개 범위 규칙
- Jjaek / ReJjaek / 책활동의 의미
- 향후 구현 시 흔들리면 안 되는 원칙

이 문서의 `초기 MVP`와 `1차 MVP` 표현은 제품 방향을 확립한 기준을 설명한다.
현재 구현 여부는 `docs/architecture/current_system.md`와 기능별 canonical spec을 따른다.

---

## 제품 방향

bookjjaek은 일반적인 짧은 글 SNS가 아니며,
책과 서재가 중요한 의미를 가지는 독서 커뮤니티다.

bookjjaek의 중심은 다음과 같다.

1. 사용자는 짹(`Jjaek`)을 남긴다.
2. 사용자는 책을 자기 서재에 담는다.
3. 사용자는 필요하면 짹에 책을 연결해 책짹을 남긴다.
4. 사용자는 다른 사람의 책과 짹을 관계에 따라 본다.
5. 사용자는 소식받기와 책친구 관계를 통해 흐름을 이어간다.

즉, 서비스의 중심축은 다음과 같다.

- `Jjaek`
- `User`
- `Follow`
- `BookFriendship`
- `Book`
- `Bookshelf`
- `BookshelfEntry`

## 핵심 용어

### 책
서비스 안에서 공통으로 참조되는 도서 정보.
개인 감정, 상태, 공개 범위는 책 자체에 저장하지 않는다.

### 서재
사용자가 자기 책 목록과 독서 상태를 쌓는 **전체 독서 공간**.
현재 구현에서는 사용자 프로필 안에서 Bookshelf 단위로 책 목록을 관리한다.

### 책장
서재 안에 들어가는 **하위 컬렉션 단위**.
현재 구현에서는 기본 책장 “내 책장”과 일반 책장을 `Bookshelf` 모델로 다룬다.
각 책장은 visibility, color_key, position을 가진다.

### 서재 항목
특정 사용자가 특정 책을 자기 서재 안 어떤 책장/목록 문맥으로 가지고 있는지를 나타내는 기록.
현재 구현에서는 `BookshelfEntry`가 하나의 `Bookshelf`에 속한다.

### 대표 상태
한 서재 항목이 가지는 기본 상태.
초기 버전에서는 아래 3개만 허용한다.

- 읽고 싶어요
- 읽는 중
- 읽었어요

대표 상태는 한 서재 항목당 1개만 가진다.

### 스티커
대표 상태와 별개로, 책에 대한 감정이나 의도를 표현하는 보조 태그.
한 서재 항목에 여러 개를 붙일 수 있다.

예:
- 좋았어요
- 너무 좋았어요
- 마음에 남아요
- 다시 읽고 싶어요
- 추천받았어요
- 추천하고 싶어요

### Jjaek
사용자가 남기는 기본 콘텐츠 단위.
Jjaek은 책 없이도 존재할 수 있다.
필요하면 특정 책에 연결될 수 있다.

예:
- 일반 메시지
- 사진이 포함된 짧은 글
- 링크/인용구 공유
- 저자에 대한 토론
- 한줄평
- 짧은 감상
- 긴 감상
- 쓰레드형 글

책이 연결된 `Jjaek`는 UI 문맥에서 **책짹**이라 부를 수 있다.

### ReJjaek
다른 사용자의 Jjaek을 인용하고,
그 위에 내 의견을 덧붙여 새 Jjaek을 만드는 기능.
성격상 책 상태 기록보다 **인용/응답**에 더 가깝다.

UI 문맥에서 **다시짹**이라 부를 수 있다.

### 책활동
Jjaek처럼 본문이 있는 글이 아니라,
서재 상태 변경이나 스티커 추가처럼 발생하는 활동 기록.

예:
- 어떤 책을 읽고 싶어요로 담음
- 어떤 책을 읽는 중으로 바꿈
- 어떤 책에 너무 좋았어요 스티커를 붙임

현재 구현에서는 책활동을 사용자-facing 개념으로 유지하면서,
`BookActivity`는 개인 서재 최초 추가만 이벤트로 기록한다. 상태·스티커는 개인 독서 관리로 유지한다.
세부 구현 기준과 남은 범위는 `docs/specs/book_activity_mvp.md`를 따른다.

### BookActivity
`BookActivity`는 책과 관련된 사용자 행동을
피드에서 소비하기 좋은 형태로 기록하는 **피드용 이벤트 모델**이다.

현재 기록 대상은 책을 개인 서재에 처음 담은 사건이다.
상태·스티커 변경은 새 활동을 생성하지 않으며 과거 변경 활동도 피드에서 제외한다.

중요한 점:
- `BookActivity`는 책에 대한 본문 글이 아니다.
- `BookActivity`는 `BookshelfEntry`나 `BookshelfEntrySticker` 자체를 대체하지 않는다.
- `BookActivity`의 목적은 **도메인 상태 저장**이 아니라
  **피드 노출용 이벤트 표현**이다.

### 소식받기
한 사용자가 다른 사용자의 공개 Jjaek을
자기 피드에서 받고 싶을 때 맺는 가벼운 단방향 관계.
기술적으로는 follow 개념과 대응한다.

### 책친구
신청/수락을 통해 성립하는 신뢰 관계.
책친구 공개 Jjaek을 볼 수 있는 기준이 된다.

## 관계 모델

관계 모델의 세부 MVP 기준은
`docs/specs/social_relationships_mvp.md`를 함께 본다.

이 문서는 특히 아래를 보완한다.
- `Follow` / `BookFriendship` 역할 구분
- Relationship Page
- Notification 진입점
- Comment visibility 정책

### 소식받기
의미:
- 이 사람의 공개 Jjaek을 내 피드에서 보고 싶다.

특징:
- 단방향 관계다.
- 책친구와 다르다.
- 공개 콘텐츠를 피드에 띄우는 기준이다.
- 프로필 화면에서는 **공개 짹까지 볼 수 있게 하는 가벼운 관계**로 해석할 수 있다.

### 책친구
의미:
- 이 사람과는 좀 더 안심하고 독서 기록과 Jjaek을 주고받을 수 있다.

특징:
- 신청/수락이 필요하다.
- 소식받기와 다르다.
- 책친구 공개 범위를 볼 수 있는 기준이다.
- 프로필 화면에서는 **더 넓은 짹 열람 범위와 상호작용을 여는 신뢰 관계**로 해석한다.

## 공개 범위

Jjaek의 공개 범위는 아래 3개만 둔다.

- 전체 공개
- 책친구 공개
- 나만 보기

### 전체 공개
누구나 볼 수 있다.

### 책친구 공개
작성자의 책친구만 볼 수 있다.

### 나만 보기
작성자만 볼 수 있다.

- 추천하고 싶어요

- 스티커는 여러 개 가질 수 있다.

## Jjaek과 책활동의 구분

### Jjaek
사용자가 직접 쓰는 글이다.
본문이 있다.
책에 선택적으로 연결될 수 있다.
댓글/좋아요/ReJjaek의 대상이 된다.

작성·수정 시 일반 짹, 책짹, 동아리 짹과 다시짹의 새 본문은 최대 200자이며,
댓글도 최대 200자다. 한글·영문을 차등 계산하지 않고 Unicode 코드 포인트 수로 센다.
공백과 문장부호를 포함하며, 줄바꿈은 LF로 정규화하여 한 문자로 센다.
브라우저와 서버는 같은 계산 기준을 사용하고, 다시짹의 원문은 새 본문 길이에 포함하지 않는다.
최소 작성 분량은 정하지 않으며 기존 빈 본문 검증은 유지한다.

### 책활동
개인 서재에 책을 처음 추가한 활동이다.
본문 콘텐츠와 독서 상태·스티커 관리는 분리한다.

원칙:
- 도메인 상 Jjaek과 책활동은 분리한다.
- 사용자에게는 필요 이상으로 복잡하게 드러내지 않는다.
- 피드에서는 둘을 하나의 흐름처럼 함께 보여줄 수 있다.
- 현재 구현에서는 BookActivity 모델과 프로필 최근 활동 타임라인 노출이 도입되어 있다.
- 홈 피드 합성은 구현되어 있으며, 현재 책장 visibility로 기존 관계 범위를 추가 제한한다. books/:id에는 합성하지 않는다.

### BookshelfEntry / BookshelfEntrySticker / BookActivity 책임 경계

#### BookshelfEntry
- 사용자가 특정 책을 어떤 상태로 가지고 있는지 저장하는 **현재 상태 모델**이다.
- 대표 상태의 source of truth다.
- 피드 이벤트 자체를 표현하지 않는다.

#### BookshelfEntrySticker
- 특정 서재 항목에 어떤 스티커가 붙어 있는지 저장하는 **연결 모델**이다.
- 스티커 부착 상태의 source of truth다.
- 피드 이벤트 자체를 표현하지 않는다.

#### Jjaek
- 사용자가 직접 쓴 **본문 글 모델**이다.
- 책 없이도 존재할 수 있고, 필요하면 특정 책에 연결될 수 있다.
- 감상, 생각, 인용, ReJjaek을 담는다.
- 댓글/좋아요/ReJjaek의 대상이 된다.

#### BookActivity
- 개인 `BookshelfEntry` 최초 추가에서 파생되는 **피드용 이벤트 모델**이다.
- 어떤 변화가 있었는지를 시간순으로 보여주기 위한 표현 계층이다.
- 상태의 source of truth가 아니다.
- 책에 대한 자유 본문 글도 아니다.

즉:
- 현재 상태는 `BookshelfEntry`
- 현재 스티커 부착 상태는 `BookshelfEntrySticker`
- 본문 글은 `Jjaek`
- 피드용 활동 이벤트는 `BookActivity`

## ReJjaek 규칙

ReJjaek은 새 Jjaek이지만,
원문 권한을 절대 넘어서면 안 된다.

개인·동아리 다시짹 A/B/C의 공유 경로와 원문 삭제 후 처리는
`docs/specs/group_sharing_requotes.md`, 다시짹 목록 조회와 노출 범위는
`docs/specs/requotes_mvp.md`를 canonical 기준으로 본다. 아래 삭제 후 private 전환과
개인 영역 중복 제한은 개인 다시짹 A에 적용하며 동아리 인용 B/C에 일반화하지 않는다.

### 기본 규칙

1. ReJjaek은 원문보다 넓게 공개할 수 없다.
2. 원문이 나만 보기이면 ReJjaek할 수 없다.
3. ReJjaek 가능 여부의 핵심 기준은 **BookshelfEntry 존재 여부가 아니라 원문 접근 권한**이다.
4. ReJjaek은 원문 내용을 복사 저장하지 않고 참조한다.
5. 원문이 수정되면 ReJjaek의 quoted block도 최신 원문을 보여준다.
6. 원문 또는 ReJjaek 본문이 실제 수정된 시각을 표시하며 수정 이력 전체 조회는 제공하지 않는다.
7. ReJjaek 조회 시에도 원문 접근 권한을 다시 검사한다.
8. 원문이 삭제되지 않았지만 private_jjaek/book_friends 변경이나 관계 변경으로 현재 사용자에게 보이지 않으면,
   해당 사용자에게는 ReJjaek도 비노출한다. 이 경우 ReJjaek을 자동으로 private_jjaek으로 전환하지 않는다.
9. 개인 다시짹 A의 원문이 hard delete되거나 댓글을 보존하는 tombstone이 되면 ReJjaek은 삭제하지 않고 private_jjaek으로 전환한다.
   다른 사용자 홈 피드, 프로필, 책 상세, 검색 결과, 상세 접근에서는 노출하지 않는다.
   ReJjaek 작성자 본인의 홈 피드/프로필/상세에서는 보일 수 있다.
10. 개인 다시짹 A의 hard delete된 원문 quoted block 위치에는 작성자 본인에게만
    “원문이 삭제되어 나만 볼 수 있습니다.” 안내를 표시한다.
    안내에는 원문 작성자 표시 이름, 원문 종류(짹/책짹), 원문 삭제 시각만 남긴다.
    원문 본문, 책 제목/메타데이터, 원문 내용 snapshot, avatar snapshot은 저장하거나 표시하지 않는다.
11. 개인 다시짹 A는 공개 화면에 “삭제된 원문입니다” placeholder를 표시하지 않는다.
12. 초기 MVP에서는 구현 단순성과 권한 일관성을 위해
   ReJjaek이 다른 ReJjaek을 다시 인용하는 **중첩 ReJjaek**은 허용하지 않는다.
13. 개인 영역에서 한 사용자는 같은 원문 Jjaek을 한 번만 ReJjaek할 수 있다.
    동일 사용자 + 동일 원문 중복 ReJjaek 요청은 새 ReJjaek을 만들지 않는다.
    다른 사용자가 같은 원문을 ReJjaek하는 것은 허용한다.
14. 원문 hard delete로 인해 기존 개인 ReJjaek이 deleted-source private 상태가 된 경우는 별도 상태이며,
    살아 있는 원문에 대한 중복 ReJjaek 제한과 구분한다.
15. ReJjaek의 1차 작성 진입 UX는 아래 `ReJjaek 1차 UX` 기준을 따른다.
    이를 별도 모델로 곧바로 분리하지는 않으며,
    우선 `Jjaek`의 `quoted_jjaek` 문맥으로 유지한다.

### 예시

원문이 전체 공개:
- ReJjaek 공개 범위: 전체 공개 / 책친구 공개 / 나만 보기 가능

원문이 책친구 공개:
- ReJjaek 공개 범위: 책친구 공개 / 나만 보기만 가능
- 전체 공개 불가

원문이 나만 보기:
- ReJjaek 불가

## 댓글과 좋아요 원칙

초기 버전에서는 댓글과 좋아요의 대상은 `Jjaek`으로 한정한다.

원칙:
- 댓글/좋아요는 **해당 Jjaek을 볼 수 있는 사람만** 가능하다.
- 즉, 상호작용 가능 범위는 공개 범위보다 넓어질 수 없다.
- 초기 MVP에서는 작성자가 개별 Jjaek마다 댓글 허용 여부를 따로 조절하는 기능은 두지 않는다.

### 댓글
- 전체 공개 Jjaek: 로그인 사용자는 허용

## 피드 원칙

피드는 서비스의 중심 모델이 아니라
도메인 모델이 만들어내는 결과물이다.

초기 MVP의 Jjaek 피드는 아래를 우선 대상으로 삼았다.

- 소식받는 사람의 전체 공개 Jjaek
- 소식받는 책친구의 책친구 공개 Jjaek

현재 홈 피드는 Jjaek과 본인·소식받는 accepted 책친구의 BookActivity를 합성한다.
소식받는 사람의 전체 공개 책활동까지 넓히는 정책은 별도 후속 검토 대상이다.

원칙:
- 피드는 `Post` 단일 테이블 중심으로 설계하지 않는다.
- Jjaek과 책활동은 각 도메인 모델의 결과로 함께 다룬다.

## 1차 MVP 화면 경계

초기 MVP에서는 각 화면의 책임을 작게 유지한다.
하나의 화면이 너무 많은 쓰기 기능과 보조 위젯을 동시에 가지지 않도록 한다.

### 홈
- 홈은 **Jjaek 흐름 중심 화면**으로 둔다.
- 초기 홈에는 아래만 우선 포함한다.
  - 내가 남긴 짹
  - 소식받는 사람의 전체 공개 짹
  - 소식받는 책친구의 책친구 공개 짹
  - 현재 사용자를 대상으로 한 visible `profile-context Jjaek`
  - 일반 `짹` 입력창
  - 책 검색 진입
  - 내 서재 보기 진입
- 아래 요소는 초기 홈의 필수 범위에 포함하지 않는다.
  - 책친구 요청 위젯
  - BookActivity 요약 위젯
  - 그룹 관련 위젯

### 프로필
- 프로필(`users/:id`)은 **관계 맺기 + 관계에 따라 그 사람의 책과 짹을 보는 화면**으로 둔다.
- accepted 책친구의 타인 프로필에는 해당 사람을 문맥으로 삼는 `profile-context Jjaek` 입력 진입을 둔다. 자기 프로필의 일반 Jjaek은 홈(`/`)에서 작성한다.
- 이 입력은 DM이 아니라, `target_user_id`를 가지는 공개/관계기반 `Jjaek` 작성이다.
- 이 문맥의 `Jjaek`는 `A가 B에게 남긴 짹`처럼 표시할 수 있다.
- 관계에 따라 아래 노출 범위를 다르게 둔다.
  - 아무 관계 없음:
    - 공개 책장에 담긴 책 목록만 본다
    - 공개 짹은 보지 않는다
    - 책친구 공개 짹은 보지 않는다
    - profile-context 입력창은 보지 않는다
  - 소식받기(`Follow`)만 함:
    - 공개 책장에 담긴 책 목록을 본다
    - 공개 짹을 본다
    - 책친구 공개 짹은 보지 않는다
    - profile-context 입력창은 보지 않는다
  - accepted 책친구:
    - 공개 책장에 담긴 책 목록을 본다
    - 공개 짹과 책친구 공개 짹을 본다
    - profile-context 입력창을 본다
  - 본인:
    - 자신의 전체 서재와 전체 짹을 본다
    - 자기 프로필에는 profile-context 입력창을 두지 않는다

### 서재
- 서재는 **내 독서 공간 전체**를 뜻한다.
- 현재 구현에서는 기본 책장 “내 책장”과 일반 책장을 `Bookshelf` 모델로 다룬다.
- 프로필 화면의 책장 영역은 **책 목록과 상태/스티커 관리**에 집중한다.
- 타인 프로필의 책 목록은 Bookshelf visibility 기준으로 접근 가능한 책장만 보여준다.
- 서재 화면은 책짹을 책/서재 문맥에서 다시 모아보는 진입점이 될 수 있다.

### 책 상세
- 책 상세(`books/:id`)는 **책 문맥 화면**으로 둔다.
- 책 상세에는 아래 요소를 함께 둔다.
  - 책 메타데이터
  - 그 책에 연결된 visible 책짹 목록
  - 책짹 입력창
  - 대표 상태 선택
  - 스티커 선택
- 즉, 초기 MVP에서는 책 상세 안에서
  **서재 수정과 책짹 작성이 함께 일어날 수 있다.**
- 다만 내부 도메인 저장 책임은 계속 분리한다.
  - 상태/스티커 저장은 `BookshelfEntry`
  - 책짹 저장은 `Jjaek`
- 같은 화면에 공존하더라도 저장 책임은 합치지 않는다.
  - 상태/스티커 저장은 별도 form
  - 책짹 작성은 별도 form
  - 저장 엔드포인트도 분리한다
- 다만 사용자가 검색 결과의 `책 상세 보기`를 통해 먼저 들어올 수 있으므로,
  `books/:id` 접근 자체는 `BookshelfEntry`가 없어도 허용할 수 있다.
- 이 경우 책 상세는 **읽기 전용 상태**로 동작한다.
  - 책 메타데이터는 볼 수 있다.
  - 다른 사람의 visible 책짹 목록은 볼 수 있다.
  - 하지만 상태/스티커 저장과 책짹 작성은 열리지 않는다.
- 즉, 상태/스티커 변경과 Jjaek 작성은
  **현재 사용자의 BookshelfEntry가 있을 때만** 가능하다.
- 같은 화면의 입력 영역 버튼 문구는 `책짹`으로 둔다.
- 책 상세에 관계 위젯, 홈 요약 위젯, BookActivity 요약까지 함께 싣는 복합 대시보드는 두지 않는다.

### Jjaek 작성
- 일반 Jjaek 작성의 기본 진입은 홈에 둔다.
- 책이 연결된 Jjaek 작성의 기본 진입은 책 상세 안에 둔다.
- UI 문맥상 아래처럼 부를 수 있다.
  - 일반 작성: `짹`
  - 책이 연결된 작성: `책짹`
  - 인용/응답 작성: `다시짹`
- 세 경우 모두 기본 모델은 `Jjaek`로 유지한다.

### Jjaek 표시 규칙 1차

- 일반 `Jjaek`는 기본적으로 `짹`으로 표시할 수 있다.
- `target_user_id`가 있는 `Jjaek`는 `A가 B에게 남긴 짹`처럼 표시할 수 있다.
- 다만 기존에 저장된 작성자와 대상 사용자가 같은 self-target Jjaek은 일반 `A의 짹`처럼 표시한다.
- `book_id`가 있는 `Jjaek`는 `A가 X에 대해 남긴 책짹`처럼 표시할 수 있다.
- `quoted_jjaek_id`가 있는 `Jjaek`는 `A가 B의 짹을 다시짹`처럼 표시할 수 있다.
- `target_user_id`와 `quoted_jjaek_id`가 함께 있는 경우에도, 1차 MVP에서는 `다시짹` 문맥을 우선해 표시할 수 있다.
- `book_id`와 `quoted_jjaek_id`가 함께 있는 경우에도, 1차 MVP에서는 `책짹`보다 `다시짹` 문맥을 우선해 표시할 수 있다.
- `book_id`와 `target_user_id`가 함께 있는 경우에는 1차 MVP에서 `책짹` 문맥을 우선하고,
  사람 문맥은 후속 단계에서 더 세분화할 수 있다.
- 이 표시 규칙은 UI용 해석이며, 기본 모델은 계속 `Jjaek`로 유지한다.
- 동아리 짹·책짹·다시짹의 문맥 설명은 기존 문장 안에서 동아리 이름 링크 바로 앞에 작은 중립적인 `동아리` 배지를 표시한다. 별도 정보 행이나 강조 카드를 추가하지 않는다.
- 타인에게 남긴 짹은 받는 사람 이름 앞에 기존 avatar helper의 약 20px 프로필 썸네일을 표시하고, 썸네일과 이름을 받는 사람의 프로필 링크에 함께 넣는다. 작성자와 받는 사람을 별도 영역으로 분리하지 않는다.
- 일반 게시물 작성자 이름에는 문맥 설명용 썸네일을 추가하지 않는다.

### 게시물 복귀 경로

- 짹·책짹 상세, 숨김·삭제 상세와 관련 작성·수정 화면은 돌아가기 링크를 제공한다.
- 목록 → 상세 → 작성·수정 흐름은 단일 `return_to`에 원래 내부 경로를 담아 전달한다. 개인 게시·수정 성공 후 상세 화면과 검증 실패 화면에서도 검증된 경로를 유지한다.
- 허용 목적지는 홈, 발견, 알림 목록, 사용자 프로필·접근 가능한 서재, 책 검색 결과, 책 상세(기존 `group_id` 문맥 포함), 동아리 목록·상세, 관리자 User/Group 콘텐츠 목록, 동아리 콘텐츠 관리 목록, 접근 가능한 다시짹 목록과 삭제되지 않은 짹 상세다. 서재의 `bookshelf_id`, `sort`와 검색 결과의 `query`, `page`, `group_id`를 보존하며 책장과 동아리 접근 권한을 재검사한다.
- 관리자 User 콘텐츠 목록의 `content`, `q`, `location`, `status`, `sort`, `all_page`를 보존한다. Group 콘텐츠 목록의 `content`, `content_q`, `content_status`, `content_sort`, `all_page`와 관리자 Group 목록의 `q`, `group_type`, `status`, `operation_status`, `sort`, `page`를 보존한다.
- GET route allowlist로 경로를 정규화하고 목적지의 현재 Pundit 접근 권한을 확인한다. 외부 URL, protocol-relative URL, 제어 문자·역슬래시, 미허용 경로, 존재하지 않는 대상과 접근 불가능한 경로는 거부한다.
- 알 수 없는 query key와 중첩 `return_to`는 전파하지 않으며, `request.referer`를 복귀 기준으로 사용하지 않는다. 유효한 복귀 경로가 없으면 기존 게시 문맥의 접근 가능한 기본 화면 또는 홈으로 돌아간다.
- 돌아가기 표현은 왼쪽 화살표와 돌아가기 텍스트로 통일하고 페이지 본문 최상단 왼쪽, 제목·주요 카드 위에 배치한다. 관리 화면의 명확한 목적지 문구와 폼 취소·모달 닫기는 유지한다. 홈·발견·알림 등 최상위 화면에는 추가하지 않는다.
- 발견·알림의 게시물 링크는 출발 목록을 전달한다. 접근 불가능한 알림 대상의 안전한 fallback과 프로필·동아리 알림 경로는 유지한다.
- 상세에서 시작한 관리자·동아리 숨김/복구는 완료·취소 후 출발 목록 문맥을 가진 상세로 돌아간다. 기존 목록 직접 액션의 `return_to=group_content`와 검색·필터 경로는 별도로 유지한다.
- 삭제 후에는 검증된 출발 문맥으로 복귀하되, 삭제된 자기 상세로 돌아가지 않는다. 유효한 문맥이 없으면 개인 짹은 홈, 동아리 짹은 접근 가능한 동아리 상세 또는 동아리 목록으로 복귀한다.
- Navbar 책 검색은 입력 전용 모달에서 GET으로 `/book_search`에 제출하며 group_id를 자동 전달하지 않는다. 검색 입력과 결과는 기존 `/book_search` 독립 페이지에서도 함께 표시한다. 검색어 없이도 입력 폼을 표시하고, 같은 페이지에서 다시 검색할 때 최초 출발 화면과 명시적으로 전달된 동아리 작성 문맥을 유지한다. 검색 페이지는 검증된 `search_origin`의 출발 화면으로, 책 상세·미리보기·서재 등록 후 상세는 `return_to`의 검색 결과로 돌아간다. 검색어·페이지·명시적인 group_id와 검색 페이지의 출발 문맥을 보존하며 `search_origin`은 복귀 용도로 한 단계만 검증·보존한다. 출발 문맥이 없으면 해당 동아리 또는 본인 서재로 복귀한다. 세부 정책은 `docs/specs/book_search_mvp.md`를 따른다. 게시 위치는 기존 책 상세 작성 폼에서 선택한다.

### ReJjaek 1차 UX

- ReJjaek은 별도 모델이 아니라 `Jjaek`의 `quoted_jjaek` 문맥으로 해석한다.
- 1차 MVP의 다시짹 작성 진입은 `jjaeks/:id` 상세 화면에 둔다.
- 다시짹은 책짹의 하위 기능이 아니라, 특정 짹에 대한 인용/응답 작성이다.
- 원문이 private이거나 원문 자체가 ReJjaek이면 다시짹 작성 진입을 노출하지 않는다.
- 이미 같은 원문을 ReJjaek한 사용자에게는 새 ReJjaek 버튼을 숨기거나 “내 다시짹 보기”로 대체할 수 있다.
- MVP에서는 버튼 숨김만으로 충분하다.
- 다시짹은 원문보다 넓은 공개 범위로 작성할 수 없다.
- 살아 있는 원문의 접근 권한이 사라지면 연결을 유지한 채 다시짹도 일반 목록에서 비노출한다. 원문 삭제 뒤에는 개인 다시짹 A만 작성자 전용으로 전환하고, B·C는 목적지 동아리 접근 권한 안에서 보존한다.
- 상세 화면과 home·profile·book·group 카드의 작성 진입은 현재 ReJjaek policy와 목적지별 중복 제한을 따른다.
- 개인·동아리 다시짹의 문맥 설명은 원문 작성자 이름 앞에 받는 사람과 동일한 약 20px 프로필 썸네일을 표시한다. 일반 짹과 책짹 원문 모두 적용하며, 썸네일과 이름은 원문 작성자의 프로필로 연결한다.
- 원문이 삭제되거나 열람 불가능하면 기존 비공개 처리를 유지하고 원문 작성자의 썸네일과 프로필 정보를 노출하지 않는다.

### 검색 결과
- 검색 결과는 우선 **책 상세 진입**을 기본 흐름으로 둔다.
- 검색 결과에서 바로 여러 쓰기 동작을 수행하지 않고, 책 상세로 진입한 뒤
  상태/스티커/책짹 상호작용을 수행한다.
- 다만 검색 결과 화면에서는 **`서재에 담기`** 용어를 사용한다.
- 여기서 `서재에 담기`는 외부 검색 결과의 책 정보를
  우리 서비스의 DB/서재로 가져오는 **첫 등록(import) 동작**을 뜻한다.
- 즉:
  - 검색 결과 버튼: `서재에 담기`
  - 이 동작으로 책이 우리 DB와 내 서재에 처음 등록된다
  - 그 다음부터는 `books/:id`에서 상태/스티커와 Jjaek을 다룬다

### 현재 UI 용어
- 사용자에게 보이는 홈·내·개인 피드는 문맥에 맞는 `소식` 표현을 사용한다. 기술적인 feed 명칭, 홈 구조와 조회 정책은 유지한다.
- 검색 결과 버튼: `서재에 담기`
- 홈의 일반 작성 버튼: `짹`
- 책 상세의 책 연결 작성 버튼: `책짹`
- 인용/응답 작성 버튼: `다시짹`
- 자기 게시물 다시짹 허용 여부를 포함한 기존 권한과 다시짹 동작은 유지한다.
- 책 상세의 상태/스티커: 저장 버튼 없이 항목별 클릭 즉시 저장

### 홈 피드와 책활동
- 현재 홈 피드는 Jjaek과 BookActivity를 함께 보여준다.
- 현재 `BookActivity`는 개인 `BookshelfEntry` 최초 추가만 기록하고, 상태·스티커 변경 활동은 생성하거나 피드에 표시하지 않는다.
- 홈 피드의 BookActivity 노출 범위는 현재 사용자와 소식받는 accepted book_friend로 제한한다.
- 책친구 관계만으로는 상대의 Jjaek과 BookActivity가 홈에 자동 편입되지 않는다.
- follow-only / stranger의 BookActivity는 public 책장인 경우에도 홈 피드에 노출하지 않는다.
- `BookActivity`는 `BookshelfEntry`, `BookshelfEntrySticker`, `Jjaek`의
  source of truth를 대체하지 않는다.
- 현재 책장 공개 범위와 서재 항목 제거 시 활동 정리 기준은 `docs/specs/book_activity_mvp.md`를 따른다.

## 현재 구현: 한 서재 안 여러 책장 지원

현재 구현은 사용자마다 하나의 전체 서재를 가지고, 그 안에 여러 `Bookshelf`를 둘 수 있는 구조를 사용한다.

현재 Bookshelf 정책의 세부 기준은 아래 문서를 따른다.

- 도메인/모델 정책: `docs/specs/bookshelf_foundation.md`
- 프로필 UI 정책: `docs/specs/bookshelf_ui.md`

현재 구현 기준:

- 모든 사용자는 기본 책장 “내 책장”을 가진다.
- 한 사용자는 여러 일반 책장을 만들 수 있다.
- 각 Bookshelf는 `public`, `book_friends`, `private` visibility를 가진다.
- 프로필 화면에서 다른 사용자가 보는 책 목록은 Bookshelf visibility를 기준으로 제한된다.
- 본인은 자신의 모든 책장을 볼 수 있다.
- accepted book_friend는 `public` + `book_friends` 책장을 볼 수 있다.
- follow-only / stranger는 `public` 책장만 볼 수 있다.
- 한 사용자 기준 같은 책은 하나의 `BookshelfEntry`만 가진다.
- 같은 책을 다른 책장에 넣는 것은 중복 추가가 아니라 기존 `BookshelfEntry.bookshelf_id`를 바꾸는 책장 이동으로 처리한다.

여기서 한국어 용어 해석은 다음과 같이 둔다.

- 서재 = 사용자 전체 독서 공간
- Bookshelf = 서재 안의 책장

## 현재 구현: Group

`Group`과 `GroupMembership`, 동아리 Jjaek·Comment, 가입·초대·승인·운영 lifecycle,
개인·동아리 다시짹과 moderation은 현재 구현되어 있다.

현재 구현 상태는 `docs/architecture/current_system.md`, 제품·접근 정책은
`docs/specs/groups_mvp.md`, lifecycle은 `docs/specs/account_group_lifecycle.md`,
개인·동아리 다시짹은 `docs/specs/group_sharing_requotes.md`, moderation은
`docs/specs/moderation_mvp.md`를 따른다.

Classroom과 관리형 학생 계정은 현재 Group 구현과 구분하는 주요 후속 개발 대상이다.
프로젝트별 별도 Group 정책은 별도 후속 확장이다. Group 정책을 이 기능들에 자동 적용하지 않는다.

---

## 주요 후속 설계 대상: Classroom

교사·교실·관리형 학생 계정과 학생 로그인, `ClassroomMembership`의 역할·접근 경계를
별도 설계한다. 교실 전용 짹·책짹·댓글, 교실 운영 종료와 읽기 전용 아카이브도
같은 설계에서 다룬다. Group의 승인 lifecycle이나 데이터 모델을 Classroom에 자동으로
적용하지 않는다. `ClassroomJjaek`, `ClassroomComment`는 설계 후보이며 실제 구현 구조는
후속 설계에서 확정한다.

교실 결과물의 일반 SNS 공개는 학생 동의, 교사 검토, 개인정보 보호를 포함해 후속 검토한다.
자동 공개하지 않는 경계와 관리형 학생 계정의 현재 목표 정책은
`docs/specs/moderation_mvp.md`를 따른다. 이 절은 Classroom의 상세 구현 spec이 아니다.

## 향후 확장: 자동 생성 학생 계정과 일반 사용자 전환

교사가 자동 생성한 학생 계정은
처음에는 Classroom 기반 관리형 계정일 수 있다.

하지만 사용자가 원하면
기존 활동 기록을 유지한 채 일반 사용자 계정으로 전환할 수 있어야 한다.

원칙:
- 새 계정을 따로 만드는 것보다 기존 계정을 승격하는 방향을 우선한다.
- 기존 서재와 Jjaek 기록은 유지한다.
- Classroom 기반 사용에서 개인 서재 기반 사용으로 이어질 수 있어야 한다.

이 기능은 현재 Group 구현 범위에 포함하지 않고,
Classroom 정책과 함께 후속 단계에서 검토한다.

## 설계 원칙 요약

1. 책은 공용 정보다.
2. 서재는 사용자 전체 독서 공간이다.
3. 책장은 서재 안의 하위 컬렉션이다.
4. 대표 상태는 1개, 스티커는 여러 개다.
5. Jjaek은 사용자의 기본 콘텐츠 단위이며, 책은 선택적으로 연결된다.
6. 소식받기와 책친구는 다른 관계다.
7. 공개 범위는 전체 공개 / 책친구 공개 / 나만 보기로 제한한다.
8. ReJjaek은 원문 권한을 넘을 수 없다.
9. 피드는 도메인의 결과물이지 중심 모델이 아니다.
10. 개인 서재와 개인 간 관계는 제품의 핵심이며, 현재는 Group과 moderation까지 구현 범위가 확장되었다.
11. 한 서재 안 여러 책장과 책장 공개/비공개는 현재 Bookshelf 정책을 따른다.
12. Classroom과 관리형 학생 계정 전환 흐름은 후속 확장으로 남긴다.
