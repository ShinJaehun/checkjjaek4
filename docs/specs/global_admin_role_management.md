# 시스템 관리자 권한 부여·회수 및 감사 정책

## 상태와 목적

이 문서는 복수의 시스템 관리자(`global_admin`)를 운영하기 위한 서버 전용 권한 부여·회수 절차의 구현 기준이다. 현재 구현 설명은 `docs/architecture/current_system.md`, Pundit 권한 경계는 `docs/architecture/authorization.md`, 일반 moderation 정책은 `docs/specs/moderation_mvp.md`를 따른다. 이 문서의 역할 관리 조치는 일반 계정·콘텐츠 moderation과 별개다.

현재 `users.global_admin`은 기본값 `false`, `null: false`인 boolean이며 복수 관리자 수를 제한하는 DB 제약은 없다. 시스템 관리자 권한은 기존 `global_admin?` 검사와 Pundit policy로 판단한다. Devise 인증에는 `database_authenticatable`, `registerable`, `recoverable`, `rememberable`, `validatable`이 사용된다. 회원가입과 계정 수정의 허용 파라미터에는 `global_admin`이 없다. 현재 관리자 User inventory에는 역할 필터와 badge가 있지만 역할 변경 UI·controller·service·운영 명령은 없다.

기존 `ModerationAction`은 계정·콘텐츠·Group moderation 감사이며, `GroupLifecycleEvent`와 `GroupMembershipEvent`는 Group 운영·membership 사건을 기록한다. 시스템 관리자 역할 변경에는 이 기록들을 재사용하지 않고 별도의 `GlobalAdminRoleChange`를 둔다. 기존 관리자에게 과거 역할 부여 이력이 없을 수 있으므로, 배포 이전 변경을 새 감사 기록에서 추정하거나 실제 실행된 것처럼 소급 생성하지 않는다.

## 권한 부여·회수 정책

- 여러 User가 동시에 `global_admin`일 수 있으며 관리자끼리 동등한 기존 운영 권한을 가진다.
- 일반 시스템 관리자는 자기 자신을 포함해 다른 User의 시스템 관리자 권한을 부여하거나 회수할 수 없다. 기존 웹 관리자 화면과 일반 moderation policy에는 역할 변경 권한을 추가하지 않는다.
- 역할 변경은 서버 접근 권한을 가진 운영자가 전용 Rails 명령으로만 수행한다. 별도 Owner/Super Admin 역할이나 새로운 인증 체계는 도입하지 않는다.
- 부여 대상은 이미 존재하는 정상 활성 User다. `withdrawn_at`과 `suspended_at`이 모두 없어야 한다. 현재 `User#active_account?`는 탈퇴만 확인하므로 이 메서드 하나로 대상 적격성을 판정하지 않는다.
- 회수 대상은 현재 `global_admin?`인 User다. 회수 후에도 정상적으로 로그인하고 운영할 수 있는 활성 시스템 관리자가 최소 한 명 남아야 한다. 현재 구현에서 이 수는 `global_admin: true`, `withdrawn_at: nil`, `suspended_at: nil`이며 Devise 인증이 가능한 계정만 세어 판단한다. 정지·탈퇴한 관리자 계정은 마지막 활성 관리자 보호를 위한 수에 포함하지 않는다.
- 이미 관리자에게 다시 부여하거나 관리자가 아닌 User에게 회수를 요청하면 오류로 종료한다. 이 경우 역할 상태와 감사 기록은 변하지 않는다.
- 회수 이후에도 일반 User 계정과 기존 콘텐츠·관계·일반 권한은 유지한다. 역할 회수는 계정 정지나 탈퇴가 아니다.
- 역할 부여·회수는 기존 `global_admin` boolean과 Pundit 구조를 사용한다. 관리자 간 계정·콘텐츠 제재 금지 및 Group authority의 기존 예외는 변경하지 않는다.

## 서버 운영 절차와 실행자 식별

구현 시 `global_admin:grant`와 `global_admin:revoke`에 해당하는 전용 Rails task 또는 동등한 서버 전용 명령을 제공한다. 명령은 대상 User ID와 확인용 이메일을 받아 같은 계정인지 검증하고, 변경 사유를 필수로 받는다. 실행 직전 대상의 계정 상태·현재 역할·요청 동작을 표시해 명시적 실행 확인을 받는다. 명령 실행에 필요한 서버 접근과 애플리케이션 환경·DB 접근은 기존 서버 운영 권한으로 제한한다. 웹 endpoint는 만들지 않는다.

명령 인자에 입력된 실행자 이름을 검증된 신원으로 취급하지 않는다. 명령은 실행 환경에서 확인 가능한 OS 프로세스 계정, 서버 식별 정보, 실행 시각과 실행 식별 정보를 기록하고, 동일한 실행 식별 정보를 서버 운영 로그에도 남겨 두 기록을 대조할 수 있게 한다. 이 정보가 공유 배포 계정이나 공용 서버 계정을 가리킨다면 실제 명령을 입력한 개인까지 확인했다고 표시하지 않는다. 사유·대상 정보가 일반 셸 기록이나 공개 로그에 불필요하게 노출되지 않도록 입력·로그 방식을 구현 시 정한다.

개인별 OS 계정이나 새 인증 체계는 최초 구현의 선행 조건이 아니다. 향후 서버 운영자가 여러 명이 되어 개인별 책임 추적이 필요해지면 개인별 서버 접근, 명령 실행 로그의 신뢰성·보존, 감사 row와 서버 로그의 연결 방식을 강화한다. 그 전까지 감사 기록은 **확인 가능한 서버 실행 환경과 명령 실행**을 설명하며, 확인되지 않은 사람의 신원을 증명하지 않는다.

운영자는 변경 후 대상 상태와 새 감사 row를 확인한다. 명령의 성공 응답을 받지 못해 결과가 불명확하면 곧바로 재실행하지 않고 현재 역할과 감사 이력을 먼저 확인한다. 최초 구현에는 별도의 재시도 상태 관리나 idempotency key 체계를 도입하지 않는다.

## 감사 기록 데이터 구조

새 `GlobalAdminRoleChange`는 역할 변경 전용 기록이며 최소한 다음 값을 보존한다.

| 항목 | 의미 |
| --- | --- |
| `user_id` | 권한이 변경된 대상 User |
| `action` | `grant` 또는 `revoke` |
| `global_admin_before`, `global_admin_after` | 변경 전후의 실제 boolean 상태 |
| `reason` | 필수 변경 사유 |
| 실행 주체·환경 정보 | 확인 가능한 OS 프로세스 계정과 서버 식별 정보. 개인을 검증하지 못한 경우 이를 개인 신원으로 표시하지 않음 |
| 실행 식별 정보 | 서버 운영 로그와 같은 명령 실행을 대조하기 위한 값 |
| `created_at` | 역할 변경 감사 시각 |

`grant`는 `false → true`, `revoke`는 `true → false` 전이만 기록한다. 상태가 바뀌지 않은 중복 명령은 감사 row도 만들지 않는다. 대상 User와 감사 row 생성은 하나의 DB transaction에 넣고, 감사 저장 실패 시 User 변경도 rollback한다. 감사 기록은 생성 후 애플리케이션 경로에서 수정·삭제할 수 없도록 설계하고, 대상 User가 나중에 계정 lifecycle을 바꾸더라도 이력을 보존한다.

이 불변성은 정식 애플리케이션 운영 절차의 보장이다. 서버 운영자가 Rails console이나 DB에 직접 접근해 `global_admin`을 수정할 수 있다는 한계는 남는다. 권한 있는 직접 DB 수정까지 앱 모델과 감사 테이블만으로 완전히 통제하거나 모든 우회를 탐지할 수 있다고 주장하지 않는다. 직접 수정은 정식 운영 절차가 아니며 서버 접근·DB 운영 로그에 의존한다.

## 인증·세션 및 보안 경계

권한 회수가 commit된 뒤 시작하는 다음 요청부터 기존 로그인 세션에서도 관리자 권한이 없어야 한다. 세션 자체를 일반 User 세션으로 유지할 수 있으나 관리자 목록·상세, 운영 조치와 기타 `global_admin?` 경로는 현재 DB 역할을 사용해 거부한다. 새 로그인과 Devise remember-me로 복원된 세션도 같은 기준이다. 이미 처리 중인 요청을 소급 취소한다는 보장은 포함하지 않는다.

현재 인증은 Devise와 `current_user`를 사용하고, 별도 역할 claim이나 역할 캐시를 저장하는 코드는 확인되지 않았다. 다만 이 사실만으로 기존 세션의 권한 반영 시점을 보증하지 않는다. 구현 시 실제 HTTP 요청에서 회수 전 로그인 세션, remember-me 복원, 관리자 직접 URL과 POST가 회수 직후 거부되는지 검증한다. 필요하면 요청마다 현재 역할을 다시 읽도록 권한 경계에서 보강한다. 역할 변경 명령은 기존 웹 세션을 통해 인증되지 않으며 Pundit의 일반 moderation 권한으로 실행되지 않는다.

## 예외·실패·복구 시나리오

- 대상 User 없음, 확인용 이메일 불일치, 비정상 계정에 대한 부여, 중복 부여·회수, 마지막 정상 활성 관리자 회수, 실행 전 확인 거부는 상태와 감사 기록을 변경하지 않는다.
- 사유 누락·유효성 실패, User 저장 실패 또는 감사 저장 실패는 전체 transaction을 rollback한다. 성공 로그는 commit 이후에만 확정한다.
- 서로 다른 서버 명령이 동시에 권한을 회수해 정상 활성 관리자 수가 0명이 되는 일을 막아야 한다. 구현은 역할 변경을 직렬화할 수 있는 DB 수준 동기화와 같은 transaction 안에서 위 활성 조건을 적용한 회수 후 관리자 수를 검사한다. 정지·탈퇴 계정을 단순 `global_admin: true` 개수에 포함하거나 대상 User row만 잠그는 것으로 이 조건이 보호된다고 가정하지 않는다.
- 실행 결과가 불명확하면 역할의 현재값과 시간순 `GlobalAdminRoleChange`, 서버 실행 로그를 대조한다. 이미 적용된 부여·회수를 다시 실행하면 중복 오류로 종료되며 추가 감사 row는 남기지 않는다.
- DB 직접 변경으로 역할과 감사 이력이 불일치하면 자동으로 과거 감사 사건을 만들어 맞추지 않는다. 운영자가 서버·DB 로그를 조사하고 별도 복구 절차를 결정한다.

## 구현 단계별 계획

1. 서버 명령의 대상 식별, 사유 입력, 실행 확인, 서버 실행 정보와 로그 대조 방식을 현재 운영 환경에 맞게 확정한다.
2. `GlobalAdminRoleChange` 저장 구조와 생성 후 수정·삭제 방지, 대상 User와의 연결을 구현한다. 배포 전 기존 관리자 목록은 별도 초기 기준으로 확인하고 허구의 과거 grant 기록은 만들지 않는다.
3. 역할 변경 service에 대상 적격성, 중복 상태, 마지막 정상 활성 관리자 보호, 동시성 직렬화, User 변경과 감사 생성의 단일 transaction을 구현한다.
4. 전용 서버 명령을 service에 연결하고 웹 UI·controller에는 역할 변경 경로를 추가하지 않는다.
5. service·명령의 성공과 실패, 정지·탈퇴한 관리자만 추가로 남은 경우 및 정상 활성 관리자들의 동시 회수, 감사 rollback, 기존 세션·remember-me의 권한 회수를 검증한다. 구현 결과에 맞춰 현재 시스템 문서만 갱신한다.

## Acceptance criteria

- 서버 전용 명령은 기존 정상 활성 User에게만 권한을 부여하고, 현재 관리자에게만 권한을 회수한다. 일반 관리자와 웹 요청은 역할을 변경할 수 없다.
- 중복 요청과 마지막 정상 활성 관리자 회수는 오류이며 User 상태와 감사 row가 그대로다. 정지·탈퇴한 관리자 계정이 남아 있어도 마지막 정상 활성 관리자를 회수할 수 없으며, 동시 회수로 이 조건을 우회할 수 없다.
- 성공한 변경마다 대상, 전후 상태, 사유, 확인 가능한 실행 정보와 시각을 담은 별도 감사 row 하나가 남는다. 역할 변경과 감사 생성 중 하나라도 실패하면 둘 다 반영되지 않는다.
- 역할 회수 후 기존 로그인 세션의 다음 관리자 요청과 remember-me로 복원된 관리자 요청은 거부된다. 일반 User 권한은 유지된다.
- 명령은 실행자 이름 입력값만으로 개인을 검증했다고 기록하지 않으며, 서버 로그와 감사 기록을 실행 식별 정보로 대조할 수 있다.
- 기존 moderation policy, `global_admin` boolean, Pundit 권한 구조와 관리자 간 제재 금지 규칙은 유지된다.

## 구현 전에 확인할 쟁점

- 현재 서버·배포 환경에서 확인 가능한 OS 프로세스 계정, 서버 식별 정보와 명령 로그의 실제 수집·보존 위치. 공유 계정만 확인되는 경우 감사 화면·운영 보고에서 그 한계를 어떻게 표시할지.
- 역할 변경을 직렬화하고 마지막 정상 활성 관리자 수를 보호할 실제 DB 동기화 방식. 현재 배포 DB와 명령의 동시 실행 환경에 맞춰 정한다.
- 기존 관리자들의 배포 전 역할 상태를 초기 기준으로 확인·보존할 운영 방법. 이전 역할 부여 시각이나 실행자를 추정하지 않는다.
- 감사 이력과 서버 접근 로그의 보존 기간 및 운영자 열람 범위. 별도 관리자 관리 UI는 이번 구현 범위에 포함하지 않는다.
