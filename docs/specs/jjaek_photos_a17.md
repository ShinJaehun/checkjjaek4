# A17 — 통합 짹 사진 첨부

사용자가 승인한 2026-11-15 구현 범위다. 배포·RSpec·브라우저 검증 완료를 의미하지 않는다.
통합 짹의 책·본문·태그·알림과 Group·moderation·두 사람 전용 대화 정책은 유지한다.
사진의 권한은 [Jjaek visibility](../architecture/jjaek_visibility.md)와 `JjaekPolicy`를 따른다.

## 작성과 수정

- 공통 composer의 책 추가 옆에 사진 추가를 표시한다. 사진 0~4장과 책 0~5권은 독립적이며
  본문 필수·최대 200자는 유지한다. 수정 시 기존 사진과 새 사진을 개별 제거할 수 있다.
- 첨부 순서를 유지하고 새 사진은 뒤에 붙인다. 드래그 재정렬은 제공하지 않는다.
- 저장된 사진과 새 사진의 제거 버튼은 미리보기 우측 상단의 원형 X로 통일한다.
  44px 클릭 영역·사진 제거 aria-label·키보드 포커스를 제공한다. 제거 상태와 개수는 즉시 갱신하고
  저장된 사진의 실제 삭제는 기존처럼 짹 저장 때 수행한다.
- JPEG·PNG·WebP 원본을 장당 5MB 이하로 선택한다. 브라우저가 긴 변 2000px 이하로 축소하고
  canvas로 재인코딩해 EXIF를 제거한다. 업로드 전에 얼굴·이름·위치와 타인 공유 동의를 확인하도록 안내한다.
- 사진 안내는 상시 문구 대신 작성·수정 과정에서 사진 추가를 처음 누를 때만 native dialog로 표시한다.
  개인정보·타인 동의·베타 일일 한도(기존 서버 설정값)·짹당 4장·형식·원본 크기를 안내한다.
  취소는 안내만 닫고, 확인하고 사진 선택은 안내를 닫고 파일 선택창을 연다. 안내를 본 상태는 취소 여부와
  관계없이 같은 Turbo 초안에서 유지한다. 새 작성 과정은 다시 안내하며 이 UI는 서버 검증을 대체하지 않는다.
- 본문·공개 범위·선택 책·사진은 책 선택/취소/복귀 및 같은 탭의 Turbo 방문과 검증 실패에서 유지한다.
  초안은 브라우저 메모리에만 보관하며 다른 사용자에게 재사용하지 않는다. 성공하면 초안을 제거한다.
  전체 새로고침·탭 종료·브라우저 종료 뒤 복구는 범위 밖이다.
- 사진의 브라우저·서버 오류는 본문 content-length 오류와 같은 붉은 테두리/연한 배경/여백의
  폼 내부 `role="alert"` 영역에 표시한다. 사진 오류는 코드로 구분해 본문 오류에 중복 표시하지 않는다.
  크기·형식·처리 실패를 구체적으로 안내하고 정상 선택 사진과 본문은 유지한다.
  선택/제거로 고친 파일 오류는 지우며, 서버 한도 오류는 새 업로드가 남아 있으면 재검증 전까지 유지한다.
  새 업로드를 모두 제거하면 해당 한도 안내도 지운다. 브라우저 기본 alert로 업로드 오류를 표시하지 않는다.
- 다시짹에는 새로운 사진을 붙이지 않는다. 원문 사진은 원문의 현재 읽기 권한을 검사해 표시한다.
  A/B/C의 삭제 후 처리와 snapshot 정책은 [기존 명세](group_sharing_requotes.md)를 유지한다.

## 저장과 생명주기

- Rails multipart → 서버의 실제 바이트 형식·5MB·libvips 디코딩 검증 → 2000px WebP 재인코딩/metadata 제거
  → Active Storage → 비공개 OCI 사진 버킷을 사용한다. SVG·지원 외 형식·손상 파일은 거부한다.
  서버의 처리 자원 보호를 위해 4천만 픽셀 초과 입력도 거부한다.
- 아바타와 같은 Active Storage/S3 호환 서비스·OCI credentials·libvips를 재사용한다.
  직접 OCI 업로드, 새 저장 시스템과 VM의 영구 이미지 저장은 도입하지 않는다.
- 사진 변경·본문·책·태그·일일 업로드 이력은 DB transaction으로 함께 성공하거나 롤백한다.
  교체/개별 제거·hard delete·tombstone은 첨부를 제거하고 commit 뒤 원본과 Variant를 정리한다.
  숨김은 현재 policy에 따른 원문 열람자만 사진을 볼 수 있으며 복구를 위해 파일을 보존한다.
- staging Blob은 게시 transaction 전에 생성해 중단·롤백 후에도 정리 키를 잃지 않는다.
  실패한 업로드는 정리 job으로 제거하며, 프로세스 중단으로 남은 하루 이상 미첨부 사진은 정기 작업으로 회수한다.
  OCI 파일 삭제에 실패하면 Blob 행을 유지해 재시도한다.

## 표시와 보안 경계

- 카드에는 1장 큰 사진, 2장 좌우, 3장 큰 사진 하나와 작은 사진 둘, 4장 2×2로 표시한다.
  한 장은 원래 비율로 표시하고, 여러 장은 격자 칸을 채우도록 미리보기 가장자리를 잘라 표시할 수 있다.
  저장하는 640px 카드/1600px 확대 Variant와 갤러리 표시는 원래 종횡비를 유지한다.
- 확대는 닫기·이전/다음·사진 번호·Esc·좌우 키·모바일 swipe를 지원한다.
  원본은 카드·갤러리에서 요청하지 않는다. 별도 다운로드 버튼을 제공하지 않고 context menu와 drag를 억제한다.
  이는 완전한 저장 방지가 아니며 이미 전달된 파일·화면을 회수하지 못한다.
- 원본/Variant 모두 로그인과 `JjaekPolicy#view_photos?`를 확인하고 해당 Jjaek의 `photos` 첨부 ID로 조회한다.
  숨김 placeholder만 볼 수 있는 사람, 삭제 짹, 부모를 못 보는 사용자는 파일을 받지 못한다.
  숨김 원문을 읽을 수 있는 작성자/운영자의 기존 권한은 유지한다.
  응답 직전에 요청자의 정지·탈퇴 상태, 현재 열람 권한과 사진 첨부 소속을 다시 검사한다.
- Active Storage 기본 Blob/representation/Disk/direct-upload 라우트를 닫고 아바타도 로그인 경로로 제공한다.
  사진을 아바타 또는 다른 부모 경로에 넣어 읽을 수 없다. 아바타 기본 asset fallback과 128/512px를 유지한다.
- OCI URL로 redirect하지 않고 파일을 chunk 단위로 중계한다. `private, no-store`로 인증 응답을 캐시하지 않는다.
  임의 변환 입력을 받지 않으며 카드/확대/인증된 원본만 허용한다.
- 단일 운영 VM/웹 컨테이너에서 파일 잠금으로 디코딩·변환을 직렬화하고 libvips 동시성/캐시를 제한한다.

## 베타 한도

- 사용자 하루 신규 4장, 현재 첨부 50장, 서비스 전체 최적화 원본 1GB(1,073,741,824 bytes)가 기본이다.
  환경변수로 변경하고 운영 관리자가 신규 업로드만 중지할 수 있다. 삭제·본문 수정·기존 사진 조회는 유지한다.
- 날짜는 Asia/Seoul의 업로드 transaction 시작일이다. 성공 이력을 사진과 분리해 보존하므로 삭제 후 재업로드도 합산한다.
  PostgreSQL 공통 transaction advisory lock 안에서 한도 확인·저장·이력 생성을 직렬화한다.
  실패한 게시 요청은 성공 이력을 추가하지 않는다.
- 전체 원본 byte 합계는 staging과 정리 대기 Blob도 포함한다. 삭제 완료 전에는 여유 용량으로 돌려주지 않는다.
  동시 staging 때문에 한도가 보수적으로 거절될 수 있다. Variant·아바타·OCI 버전/미완료 multipart는 별도 운영 측정 대상이다.
  이 한도는 OCI 과금의 절대 상한이 아니다. 운영 절차는 [A17 운영 문서](../ops/jjaek_photos.md)를 따른다.
- Classroom/학생 계정과 권한 모델은 생성하지 않는다. 향후 교실 학생의 사진 업로드는 금지한다.

## 관리자 콘텐츠 사진 현황

- global admin 전용 User·Group 콘텐츠 목록의 기존 본문 메타데이터에 현재 첨부 사진만
  `사진 N장 · 합계 XKB/MB`로 표시한다. 기존 책 첨부 정보와 함께 표시할 수 있다.
- 목록 페이지의 짹 ID에 한정해 Active Storage `photos` 첨부와 Blob의 `byte_size`를 DB에서 한 번 집계한다.
  댓글·사진 없는 짹·제거된 첨부·삭제 짹은 표시하지 않는다. 다시짹은 자기 첨부만 계산하고 원문은 합산하지 않는다.
  Variant·아바타는 포함하지 않으며 다운로드·이미지 변환·추가 사진 URL을 만들지 않는다.
- 기존 global admin 권한·필터·검색·정렬·pagination을 재사용하며 일반 프로필·피드·동아리 목록에는 현황을 추가하지 않는다.

## Acceptance Criteria와 검증

1. 사진 0/1/4장과 책 5권을 동시에 작성·수정하고 순서/개별 제거/전체 제거를 확인한다. 사진만으로 게시할 수 없다.
2. MIME 위장·손상 파일·5MB 초과·4장 초과·다시짹 새 사진은 원본 게시물 변경이나 성공 한도 소비 없이 거부한다.
3. 기존 사진 교체 실패에서 본문·책·태그·공개 범위·파일을 보존한다. 삭제와 tombstone은 사진 URL을 즉시 닫는다.
4. 전체 공개·책친구·나만 보기·동아리·두 사람 대화, 관계/회원/숨김 변경 후 원본과 생성된 Variant 권한을 확인한다.
5. 다른 부모 ID·signed Blob/Variant URL·Disk URL·아바타 경로를 통한 사진 접근과 direct upload를 차단한다.
6. 삭제 후 일일 한도 유지, 동시 마지막 슬롯 경쟁, 저장 실패와 OCI 삭제 재시도, 보관/byte 한도를 확인한다.
7. 모바일 책 검색·선택 취소/복귀·Turbo 왕복과 실패 응답에서 본문/책/사진을 유지하고 성공 후 초안을 비운다.
8. 갤러리 키보드/터치·1~4장 카드·아바타 128/512·기본 아바타와 사진 없는 짹을 확인한다.
9. 안내의 서버 설정값·취소/확인·동일 초안 재진입·새 작성 초기화, 관리자 User·Group 목록의
   사진 개수/용량·책과 동시 표시·원문/Variant/제거 첨부 제외·일괄 조회·global admin 경계를 확인한다.

RSpec 코드는 `spec/requests/jjaek_photos_spec.rb`, `spec/services/jjaek_photo_changes_spec.rb`,
`spec/system/jjaek_photos_spec.rb`, `spec/requests/admin/content_photos_spec.rb`에 둔다.
실제 실행 결과는 별도 사용자 검증으로 기록한다.
